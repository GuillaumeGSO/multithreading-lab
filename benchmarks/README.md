# In-process concurrency benchmark

The Artillery suite in [`../load-tests/`](../load-tests/) measures **API/HTTP
handling**. This benchmark measures the other half: the **language
implementation** — the search algorithm and its in-process concurrency — by
calling the search functions directly inside each container, with no HTTP.

Every language runs the same canonical cases from [`cases.json`](cases.json)
(generated by [`gen_cases.py`](gen_cases.py) — see [Test cases](#test-cases)) and
times each one per concurrency mode with **warmup + median-of-N**, emitting a JSON
report. The whole sweep repeats for `ROUNDS` rounds (default 3).
[`aggregate.py`](aggregate.py) combines the reports into `compare.html` and
[`summary.md`](summary.md), reporting each value as the median across rounds with the
min–max range, so run-to-run noise is visible next to the number.

## Run it

All commands assume you are in `benchmarks/`:

```bash
cd benchmarks
```

**Everything** — build all images, bench every service, build `compare.html`:

```bash
bash run-all.sh
```

**One service** (valid names: `python` `go` `java` `nest` `csharp`):

```bash
bash run-all.sh go
```

**A subset** — only the languages you care about:

```bash
bash run-all.sh go java
```

**More iterations** for a stabler median. `run-all.sh` uses light defaults
(warmup 10 / iters 50 / throughput ops 100); each language's own default is the
heavier 20 / 100 / 200. Bump them back up for a stabler median:

```bash
BENCH_WARMUP=50 BENCH_ITERS=500 THROUGHPUT_OPS=200 bash run-all.sh
```

**Higher split degree** — push axis B harder (default 2 = "halves"; 4 = quarters):

```bash
SPLIT_DEGREE=4 bash run-all.sh
```

**Combine knobs and target one service:**

```bash
BENCH_ITERS=500 SPLIT_DEGREE=4 bash run-all.sh go
```

**View the chart** after any run:

```bash
open compare.html
```

**Rebuild the chart only** (re-aggregate existing `results/*.json`, no re-bench):

```bash
python3 aggregate.py && open compare.html
```

**More or fewer rounds** (each round benches every service once, in turn, so slow
drift on the host spreads across languages):

```bash
ROUNDS=5 bash run-all.sh
```

Each runner prints **only** its JSON to stdout (logs → stderr); `run-all.sh`
redirects stdout to `results/<lang>.r<round>.json` and stderr to
`results/<lang>.r<round>.log`. If a service fails, its `.json` is removed and the
error lands in the `.log`.

## Test cases

`cases.json` is **generated, never hand-edited.** It is the single source of truth
for every language and is baked into each image at build time, so all
implementations run byte-identical inputs — which is also what makes the
cross-language correctness check valid. Edit the generator, not the JSON.

### Principle: model real queries, not stress inputs

The grid mirrors how a letter game is actually played, not worst cases for the
brute-force scan. An earlier version used pathological inputs (20+ letter pools,
8–12 excluded hints) that no real query resembles; the crossover it implied was an
artifact of inputs nobody would send. The current grid is **balanced and realistic**
so the indexed-vs-scan numbers reflect reality.

### The grid

Built by [`gen_cases.py`](gen_cases.py) (deterministic — fixed `SEED`, so re-running
reproduces the same cases). Each case is **seeded from a real accent-free word**, so
it always returns ≥ 1 result.

- **One seed word per length** (`/search/file`, lengths 4–13). Each length uses a
  single seed for all four shapes, so the *only* variable within a length is the
  hint shape.
- **A realistic rack** — the seed's distinct letters + ~3 decoys (`RACK_DECOYS`),
  capped at 26. The content filter is meaningful but not trivial, like a real rack.
- **Four query shapes** (`SHAPES`), the axis under study:
  | Shape | Hints | Models |
  |-------|-------|--------|
  | `none` | rack only, no hints | "what can I make from these letters" |
  | `normal` | rack + 2 pinned hints (letter IS at this position) | known correct positions |
  | `excluded` | rack + 2 excluded hints (letter is NOT at this position) | letters ruled out at a spot |
  | `mixed` | rack + 1 pinned + 1 excluded | mid-game knowledge |
- **`/search/many`** gets the same four shapes over realistic racks of 7–9 letters
  (`MANY_RACKS`) — the classic "find words from my letters" query.
- **A `none-wide` case per length** — letters-only with a generous ~16-letter pool
  (`WIDE_POOL`): the "here are lots of letters, what can I build" query. The wider
  pool yields a large result set, so it checks the dispatch rule still holds when a
  letters-only search returns many words.
- **`strict` `/file` variants** of the 4 shapes (Scrabble / Countdown / anagram) — a
  *multiset* tile rack (`make_strict_rack`) with exact letter-count matching. The two
  strategies treat strict very differently (indexed compares precomputed counters;
  the scan rebuilds a `Counter` per word), so this is where the dispatch verdict could
  shift. **`strict` is `/file`-only — `/search/many` has no `strict` parameter** in
  this app, so the "any-length word from exact tiles" query isn't expressible.
- **`nopool` `/file` variants** (crossword) — hints only, empty rack: known positions
  with letters otherwise unrestricted.

Current size: 122 cases (110 file, 12 many).

### Changing the grid

Edit the knobs at the top of [`gen_cases.py`](gen_cases.py) — `FILE_LENGTHS`,
`MANY_RACKS`, `RACK_DECOYS`, `N_HINTS`, `SHAPES` — then:

```bash
python3 gen_cases.py          # rewrite cases.json
bash run-all.sh               # rebuild images (cases.json is baked in) + re-bench
```

Keep it balanced: add cases in whole shape-sets (per length / per rack) rather than
one-off entries, so no length or hint shape is over-represented. Remember every
added case runs across every language, lengthening the full sweep.

## Concurrency modes

Two independent axes, exposed as named modes. Every language implements each mode with
the **same scan algorithm**: word data (accent-free form, letter counts) is computed once
per word list, and a query prepares its letter pool once.

| Mode | Axis | Meaning |
|------|------|---------|
| `baseline` | — | single-threaded scan |
| `split` | B | one file scanned in `SPLIT_DEGREE` contiguous chunks across threads |
| `fanout` | A | one thread/task per word length (`/search/many` only) |
| `nested` | A+B | per-length fan-out where each length is *also* split — threads spawning work |
| `indexed` | — | algorithm, not concurrency: the positional-index dispatcher (`/search/file`, Python/Java/C# only) |

`split` and `indexed` apply to `/search/file`; `fanout`/`nested` apply to `/search/many`.
The split degree is `SPLIT_DEGREE` (default 2 = "first half / second half").

Results are always merged in index/length order, so every mode returns
**byte-identical** output to `baseline` — verified by per-language unit tests, and
`aggregate.py` flags any case where languages return different word counts.

## What to read in the chart

- Charts compare **one mode at a time**, the same mode for every language.
- `indexed` has its own section: it compares two algorithms (scan vs index), not
  runtimes, so it never shares a chart with the concurrency modes.
- **Sub-millisecond searches**: thread start-up and message passing usually dominate,
  so `split`/`nested` gain little or lose.
- **Python** threads share the GIL → `split`/`fanout`/`nested` cannot use the second core.
  Its `uvicorn --workers 2` edge only exists under concurrent HTTP load, not in-process.
- **Go** goroutines and **C#** ThreadPool tasks run on real threads → `nested` can
  oversubscribe the 2-CPU box.
- **Nest** uses a fixed worker pool and **Java** uses virtual threads → the extra
  `nested` work queues rather than multiplying OS threads.

## Live API

The same paths are wired into the running servers through `SEARCH_MODE`, with the same
meaning everywhere:

| `SEARCH_MODE` | `/search/file` | `/search/many` |
|---|---|---|
| `baseline` | `baseline` | `baseline` |
| `parallel` (default) | `split` | `nested` |
| `indexed` (Python/Java/C#) | `indexed` | `baseline` |

An unknown value stops the server at startup. The load tests run every service under
`baseline` and under `parallel` (see [`../load-tests/`](../load-tests/)).

## Files

- `gen_cases.py` — **generates** `cases.json` (deterministic, balanced grid — see [Test cases](#test-cases)). Edit this, not the JSON.
- `cases.json` — canonical case definitions (single source of truth, baked into every image).
- `python_bench.py` — the Python in-process runner (copied into the python image as `bench.py`).
- Go/Java/Nest/C# runners live in their own trees (`go/bench/`,
  `com.lab.search.BenchmarkRunner`, `nest/src/bench.ts`, `csharp/Bench/`).
- `run-all.sh` — orchestrator. `aggregate.py` — builds `compare.html` and `summary.md`.
  `results/` — output (gitignored).
