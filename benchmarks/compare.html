Concurrency benchmark (in-process)

Generated · · each round: median of N runs after ? warmup · split degree ? · lower is better

This calls each language's search functions directly inside its container, with no HTTP, under the same 2-CPU limit. Every language runs the same scan algorithm in the same mode, so a chart compares runtimes, not algorithms:
  • baseline: single-threaded scan.
  • split (/search/file): one word list scanned as N contiguous chunks that run concurrently.
  • fanout (/search/many): one thread or task per word length.
  • nested (/search/many): fan-out where each length is also split.
Each bar is the median across rounds; the whisker spans the fastest and slowest round. Python threads share the GIL, so its threaded modes cannot use the second core. The shortest searches take about a millisecond, so on those, starting threads can cost more than it saves.

Algorithm: scan vs positional index

Separate from the concurrency comparison. Python, Java and C# also implement a positional index for /search/file: when a hint pins a letter to a position, candidates come from the index instead of scanning every word. Their dispatcher uses the index only when such a hint exists, and the scan otherwise. Bars show the speedup of that dispatcher over the single-threaded scan (above 1 means faster).

Throughput under concurrent load

Many single-threaded scans in flight at once, bounded by 2 CPUs, each language using its own concurrency model: Python threads, Java virtual threads, Go goroutines, C# ThreadPool tasks and Node's worker pool. Higher ops/sec is better, and it is the number that compares across runtimes. Expect Python near one core, because the GIL serializes its threads. Median latency does not compare across runtimes. Python, Java, Go and C# time a scan from when it starts running: Go, C# and Python switch between running scans, which stretches each one, while Java's virtual threads run a scan to completion and make the others wait to start, so Java's figure is close to one scan's own time. Node times from submission to the worker pool, so its figure also includes the time spent queued.
